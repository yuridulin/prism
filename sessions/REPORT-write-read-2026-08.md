# Prism: итог прогонов записи и чтения (август 2026)

Стенд сравнивает пары **API + хранилище** на одном OpenAPI-контракте. Цифры сессий важнее мнения. Этот отчёт — чтобы сопоставить стенд с реальной нагрузкой в другом проекте: что именно крутили, как измеряли, какие получились пределы.

Сессии:

| Когда (UTC) | id | Профиль | Что это |
|---|---|---|---|
| 2026-08-19 15:23 | `20260819T152334-write-ceiling` | write-ceiling, 3 мин | Запись, наивные адаптеры, матрица 4×5 |
| 2026-08-19 16:51 | `20260819T165135-write-ceiling` | write-ceiling, 3 мин | Запись после COPY / ILP / line protocol / batch |
| 2026-08-20 16:49 | `20260820T164920-query-mix` | query-mix, 5 мин чтения | Чтение на годовом архиве, Go × 5 БД, наивные locf/range |
| 2026-08-20 18:06 | `20260820T180620-query-mix` | query-mix, 5 мин, `--keep` | Повтор только чтения на том же архиве после правок сторов |

Хост: Windows + Docker Desktop, data-root на `D:`. Пары **строго по очереди** (параллельный прогон ломает сравнение). Каждая пара write-ceiling: `down -v` → up только её сервисов → нагрузка → запись scorecard → wipe. Query-mix второй цикл: тома **не** удаляли.

## 1. Контракт данных

Одна точка:

| Поле | Тип | Смысл |
|---|---|---|
| `ts` | UTC timestamp | время образца |
| `tag_id` | uint32 | идентификатор ряда (не строковый label) |
| `value` | float | значение |
| `quality` | uint16 OPC DA | 192 = Good; в ingest задаётся доля Good |

Каталог тегов (`id`, `name`, `unit`) живёт отдельно; в рядах только `tag_id`.

Чтения (семантика фиксирована, диалекты БД прячутся в адаптере):

| Режим | Что должно вернуться |
|---|---|
| **locf** | last observation carried forward: последняя точка каждого `tag_id` с `ts <= at` |
| **range** | locf на `from` (флаг `carried`) **плюс все сырые точки** в `(from, to]` |
| sample / twavg | считаются в API из результата range, в scorecard не входят |

Важно для сопоставления с «нашим» range: стенд **не** даунсэмплит. Окно 30 суток × 8 минутных тегов ≈ **345 600 точек** в одном HTTP JSON-ответе. Если в бою range всегда с `GROUP BY time` / `step`, цифры range здесь будут пессимистичнее вашей нагрузки.

Транспорт измерения:

- запись write-ceiling: **HTTP** `POST /v1/write` (backpressure пары, не NATS);
- чтение query-mix: **HTTP** `POST /v1/locf` и `POST /v1/range`;
- NATS `prism.samples` на этих прогонах не участвовал.

Таймаут HTTP API (Go): **30 с**. Гистограммы Prometheus — дефолтные бакеты client_golang, верхняя граница **10 с**. p95 = 10000 ms значит «вылезли за 10 с», это не истинный квантиль.

## 2. Железо на пару (envelope)

Одинаковый лимит на **каждую** пару. Не крутили CPU/RAM «чтобы красивее».

| Сервис | CPU | RAM |
|---|---|---|
| API (один из Go / Python / C# / Rust) | 1.0 | 512M |
| Хранилище (одно) | 1.0 | 1G |
| NATS | 0.50 | 256M |
| Prometheus | 0.50 | 512M |
| Генератор (write-ceiling) | **2.0** | **1G** |
| Генератор (query-mix) | 1.0 | 512M |

Это **не** «весь хост», а cgroup одной пары. Соседние БД лабораторного стенда могли быть up, но в пару входили только её API + её БД + шина/Prometheus.

Снимок CPU/RAM — `docker stats` **после** генератора. Часто CPU API = 0%: процесс уже простаивает. Для потолка записи смотреть ingest/s и write p95, не этот CPU.

Образы БД:

| Стор | Образ |
|---|---|
| Timescale | `timescale/timescaledb:2.17.2-pg16` |
| ClickHouse | `clickhouse/clickhouse-server:24.8` |
| QuestDB | `questdb/questdb:8.2.2` |
| InfluxDB | `influxdb:2.7` |
| VictoriaMetrics | `victoriametrics/victoria-metrics:v1.110.0` |

Retention рядов (чтобы год не срезало): **400 дней** (Timescale / ClickHouse TTL / Influx / VM). Prometheus сам по себе 7d, на архив не влияет.

Порты с хоста: Go `:8081`, Python `:8082`, C# `:8083`, Rust `:8084`. QuestDB HTTP с хоста `:9001` (хостовый `:9000` занят ClickHouse native).

## 3. Запись: профиль `write-ceiling`

### 3.1 Что имитируем

«Потолок»: offer **выше**, чем 1 CPU / 512M API обязан переварить. Побеждает пара с большим **ingest/s без ошибок**; при равенстве — ниже write p95.

Живого чтения в этом профиле нет (`query.enabled: false`). locf/range в scorecard = n/a.

### 3.2 Параметры генератора

Файл: `profiles/write-ceiling.yaml`.

| Параметр | Значение | Как читать относительно боя |
|---|---|---|
| transport | HTTP | не шина |
| duration | 180 с | чистая запись, без прогрева |
| `ingest.rate` | 25 000 | **на воркер**, не суммарно |
| `ingest.workers` | 8 | суммарный offer ≈ **200 000 точек/с**, если БД успевает |
| `ingest.batch` | 250 | 250 точек в одном `POST /v1/write` |
| интервал воркера | `batch/rate` = 10 мс | если batch ушёл быстрее — воркер не спит, rate растёт |
| `tag_count` | **250** | низкая кардинальность |
| `tag_start` | 1 | теги 1…250 |
| `good_ratio` | 0.98 | 98% quality=192 |
| `out_of_order` | 0 | монотонный now() |
| `late_ms` | 0 | нет опоздавших |

Итого характер записи: **узкий набор рядов, крупные батчи, без OoO, HTTP JSON → адаптер → нативный протокол БД**. Если у вас 10k+ тегов, мелкий batch, MQTT/NATS или late data — это другой профиль (`high-cardinality`, `burst`); их полной матрицы в этих сессиях нет.

Как считается ingest/s: точки, которые генератор **успешно** сдал за 180 с / 180. Это пропускная способность пары, не NATS.

### 3.3 Как писали в БД

Два поколения адаптеров.

**Baseline** (`20260819T152334`): наивные пути. Timescale — INSERT по строкам (Rust ещё и по одному execute в транзакции). QuestDB — HTTP `/write`. VM — уже line protocol / prometheus-совместимый import. Отсюда пропасть Timescale 3–6k/s против VM ~120k/s.

**Rematch** (`20260819T165135`) — то, с чем сравнивать «честный» потолок:

| Стор | Путь записи (все четыре API, с нюансами) |
|---|---|
| QuestDB | ILP TCP `:9009`, пул соединений |
| ClickHouse | native batch / HTTP **RowBinary** `INSERT … FORMAT RowBinary` |
| Timescale | PostgreSQL **COPY** (Go `CopyFrom`, C# BINARY COPY) или **UNNEST** (Rust) |
| InfluxDB 2 | raw line protocol `POST /api/v2/write?precision=ns` |
| VictoriaMetrics | Influx line `POST /write?precision=ns` (пустое measurement, metric = `prism_sample`) |

OpenAPI, семантика locf/range, envelope не меняли.

## 4. Чтение: профиль `query-mix`

### 4.1 Что имитируем

Сначала **один и тот же годовой архив**, потом только locf и range по сетке. Живого ingest во время измерения **нет**. Seed в scorecard не входит.

Чтение гоняли только **Go × 5 БД** (не полная матрица 4×5).

### 4.2 Архив (seed)

`profiles/query-mix.yaml`, `archive.span: 365d`.

Конец архива зафиксирован: **`ARCHIVE_END = 2026-08-20T16:49:20Z`**, генератор округляет к минуте → сетка от `2025-08-20T16:49:00Z` до `2026-08-20T16:49:00Z`.

Два класса рядов (всего **80 тегов**):

| Класс | tag_id | Период | Рядов | Точек за 365d |
|---|---|---|---:|---:|
| frequent | 1…8 | **1 мин** | 8 | 8 × 525 601 ≈ **4 204 808** |
| rare | 9…80 | **1 час** | 72 | 72 × 8 761 ≈ **630 792** |
| **сумма** | | | **80** | **4 835 600** |

Seed: HTTP write, batch 2000, 4 воркера. На первом цикле заливка в каждую БД заняла 18–67 с (VM 18 с, QuestDB 19, CH 25, Influx 30, Timescale 67). Второй цикл seed не повторял (`ARCHIVE_SEED=0`, `--keep`).

Характер относительно боя:

- кардинальность **низкая** (80), не 10k;
- два этажа частоты (минута / час), без миллисекундных рядов;
- дырка между точками rare максимум **1 час** — адаптеры locf смотрят назад 2–3 часа, не 370 дней;
- качество в архиве — как у генератора archive (Good), без всплесков Bad;
- нет непрерывной записи во время чтения (нет конкуренции write/read).

Схема хранения после правок (второй цикл):

| Стор | Таблица / индекс | Сжатие / партиции |
|---|---|---|
| Timescale | hypertable 7d, индекс `(tag_id, ts DESC)`, без ts-only | compress segmentby `tag_id`, policy 12h / каждые 10 с; `work_mem=16MB`; retention 400d. WAL на томе после первого сида ещё раздут (см. диск) |
| ClickHouse | MergeTree `ORDER BY (tag_id, ts)`, **месячные** партиции `toYYYYMM` | Delta+ZSTD / Gorilla; locf сначала с lookback **2 суток**, fallback на полный max(ts) |
| QuestDB | `PARTITION BY DAY`, `tag_id SYMBOL … INDEX` | locf: `LATEST ON ts PARTITION BY tag_id`; range без лишнего `ORDER BY` |
| Influx | bucket 400d | locf: Flux `last()` в окне **3 часа**, потом pivot; range — окно as-is |
| VM | `--retentionPeriod=400d` | один `/api/v1/export` на набор тегов, lookback **2 часа**; не `last_over_time[370d]` |

### 4.3 Сетка чтения

Offer: **16 запросов/с**, **8 воркеров**. Интервал воркера = `workers/rate` = **0.5 с**. Если запрос длится дольше 0.5 с, фактический qps падает (это видно по числу queries за 5 мин: потолок ≈ 16×300 = 4800; VM дал 4287, Influx 2015).

Веса mix (после `round(weight)` locf кладётся в сетку **дважды**):

| op | weight | доля в сетке (примерно) |
|---|---:|---|
| locf | 2 | 40% |
| range 1d | 1 | 20% |
| range 7d | 1 | 20% |
| range 30d | 1 | 20% |

Наборы тегов (каждый запрос — один набор):

| set | какие id | размер |
|---|---|---:|
| frequent-1 | 1 тег из 1…8 | 1 |
| rare-1 | 1 тег из 9…80 | 1 |
| frequent-8 | все 1…8 | 8 |
| rare-8 | 8 редких | 8 |
| mixed-8 | смесь частых и редких | 8 |

Моменты locf (`at` = конец архива минус offset):

`0s, 1d, 7d, 30d, 90d, 180d, 364d`

Концы range (`to` = конец архива минус offset, `from = to − window`):

`0s, 7d, 30d, 90d, 180d`

Окна, которые не влезают в span, отбрасываются. На 365d все перечисленные влезают.

Типичный размер ответа range (сырые точки, плюс до N carried):

| Окно | frequent-8 (1/мин) | rare-8 (1/час) | mixed-8 |
|---|---:|---:|---|
| 1d | ≈ 11 520 | ≈ 192 | смесь |
| 7d | ≈ 80 640 | ≈ 1 344 | смесь |
| 30d | ≈ **345 600** | ≈ 5 760 | смесь |

p95 range почти всегда определяется хвостом **30d × frequent-8**, не locf.

RNG сетки: `rng_seed: 42` (воспроизводимый обход grid по кругу, не случайный mix на каждый тик).

### 4.4 Первый цикл чтения (наивные запросы)

Сессия `20260820T164920-query-mix`. Seed + 5 мин чтения, wipe между парами. Go only.

| Пара | seed | queries / err | locf p95 | range p95 | диск |
|---|---:|---:|---:|---:|---:|
| go-victoriametrics | 18 с | 4257 / 0 | 39 ms | 250 ms | **14.7 MiB** |
| go-questdb | 19 с | 3339 / 0 | 206 ms | 1.97 s | 304 MiB |
| go-clickhouse | 25 с | 395 / 3 | **10 s*** | **10 s*** | 131 MiB |
| go-influxdb | 30 с | **0 / 190** | **10 s*** | **10 s*** | 96 MiB |
| go-timescaledb | 67 с | 2291 / **2460** | 18 ms** | 5 ms** | **1552 MiB** |

\* 10000 ms = переполнение гистограммы 10 с (запросы висели / упирались в таймаут).  
\*\* Timescale: p95 **только по успехам**. Range был синтаксически битый (`DISTINCT ON … ORDER BY` сразу перед `UNION ALL` → 500 за ~2 ms). Цифры 18/5 ms **нельзя** читать как «Timescale самый быстрый».

Почему ломалось:

- **Influx** — Flux сканировал ~370d, pivot, потом `last()` относительно «сейчас», не относительно исторического `at`.
- **ClickHouse** — дневные партиции, locf открывал сотни parts; плюс JSON-ответ.
- **Timescale** — невалидный SQL на range; диск раздут WAL (~1 GiB) после быстрой заливки года.
- **QuestDB** — `tag_id INT` без индекса, locf шёл полным backward scan.

VM уже на наивном адаптере был единственным, кто честно держал сетку.

### 4.6 Что изменили в запросах (чтобы цифры 2-го цикла были «честными»)

| Стор | locf | range |
|---|---|---|
| VM | export 2h lookback, не 8× `last_over_time[370d]` | тот же export, seed+mid в одном проходе |
| QuestDB | `LATEST ON` + SYMBOL INDEX | UNION locf + точки окна |
| ClickHouse | `max(ts)` в 2d окне + fallback | обычный фильтр по `(from, to]`; чтение RowBinary |
| Timescale | `LATERAL … ORDER BY ts DESC LIMIT 1` | скобки вокруг UNION ALL; индекс tag+ts |
| Influx | `last()` в 3h до `at`, filter по tag_id **до** pivot | отдельный Flux на окно; locf больше не сканирует год |

Семантика ответа не менялась: range по-прежнему отдаёт все точки.

## 5. Сводка для сопоставления с боем

### Запись

На **1 CPU БД + 1 CPU API**, HTTP JSON, 250 рядов, batch 250, без OoO:

| Если в бою нужно… | На стенде это |
|---|---|
| ≤ 10k/s | запас у всех rematch-пар; смотреть p95 и диск, не ingest/s |
| ~50k/s | Timescale COPY и ClickHouse уже на грани/внутри; VM/QuestDB/Influx спокойно |
| ~100k/s+ | только VM и QuestDB ILP (и то на 250 тегах) |
| много тегов / мелкий batch / OoO | **не измеряли** этой матрицей |

Победитель записи: **VictoriaMetrics**, второй эшелон **QuestDB ILP**, дальше Influx, Timescale COPY, ClickHouse.

### Чтение (год, 80 тегов, locf + сырой range до 30d, 16 qps offer)

| Операция | Кто везёт | Кто отстаёт |
|---|---|---|
| locf | VM ≈ QuestDB (~5 ms) | Influx ~96 ms, CH/TS ~66 ms |
| range 1…30d сырьём | **VM 232 ms**, CH 418, TS 725 | QuestDB 2.2 s, Influx 7.2 s |
| диск того же архива | **VM 15 MiB** | Influx 69 → CH 236 → QDB 329 → TS ~1 GiB (WAL) |

Если боевой range всегда агрегированный (минуты/часы, не 345k raw points) — разрыв VM vs остальные **сожмётся**, locf останется показательным. Если locf «последнее значение тега» на большом каталоге (тысячи id в одном запросе) — стенд этого не делал (макс. 8 id).

Конкуренции записи с чтением нет: архив frozen. Смешанный режим (iot-steady 2k/s + locf) в этих сессиях не гоняли.

### Чего в цифрах нет

- Python / C# / Rust на query-mix (адаптеры чтения у них те же идеи, но p95 не сняты).
- `high-cardinality` (10k тегов, 4k/s) и `burst` (8k/s, 5% OoO, late 2.5 с) — профили есть, полной арены нет.
- `iot-steady` (NATS, 2k/s, 250 тегов) — на таком offer пары по rate не разъедутся.
- sample/twavg, даунсэмпл, ретеншн-политики короче года.
- Честный диск Timescale после wipe (сейчас в томе старый WAL).

## 6. Чеклист: как наложить свой профиль

Снять с боя и положить рядом:

1. **Точек/с** и **размер батча** (у нас запись: до ~200k offer, факт 34–137k; batch 250).
2. **Кардинальность** (запись 250 / чтение 80; не 10k).
3. **Период ряда** (минута и час; не 100 мс и не 1 с).
4. **Locf**: сколько tag_id в одном запросе (1 или 8) и насколько далеко `at` в прошлое (до 364d).
5. **Range**: ширина окна и **число возвращаемых точек** (сырьё vs downsample). Хвост стенда — 30d × 8 × 1/мин ≈ 345k.
6. **QPS чтения и параллелизм** (16/s, 8 воркеров; если запрос > 500 мс — qps сам падает).
7. **Пишут ли в БД во время чтения**.
8. **CPU/RAM на процесс БД и API** (у нас 1 / 1G и 1 / 512M).
9. **Протокол** (HTTP JSON vs native ILP/COPY внутри адаптера — снаружи всегда JSON).
10. **Retention и диск** после той же истории, не empty.

Исходники цифр: `sessions/<id>/comparison.yaml`, `session.yaml`, `pairs/*/pair.yaml`. Генератор: `ingest/generator/`. Профили: `profiles/write-ceiling.yaml`, `profiles/query-mix.yaml`.
